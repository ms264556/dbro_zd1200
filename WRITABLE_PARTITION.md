# The /writable partition (hda4)

The ZD1200 appliance keeps all persistent, mutable state — configuration,
certificates, SSH keys, AP firmware images, logs — on a dedicated data
partition that the stock userspace mounts at `/writable`.  On the physical
appliance this is a ReiserFS volume on the CompactFlash.  The lab reproduces
it as **hda4** on the synthetic disk.

**Short answer: the lab creates hda4 as an empty, factory-fresh ReiserFS
volume and does *not* seed any skeleton into it.**  The vendor's own first-boot
code (`sys_init` + `rc.pre_ac_init`) creates the `/writable` directory tree,
certs and SSH keys the first time the controller boots.

---

## 1. Where the image is created

`make-synthetic-cf.py` builds the whole synthetic CompactFlash
(`synthetic-cf.img`, 2 GiB) with a hand-written MBR:

| partition | sectors | size  | contents |
|---|---|---|---|
| hda1 | 2048 .. 329728   | 160 MiB | boot area, seeded with the root ext2 tree (`/boot`) |
| hda2 | 329728 .. 657408 | 160 MiB | root image A (boots `root=/dev/hda2`) |
| hda3 | 657408 .. 985088 | 160 MiB | root image B / dual image |
| hda4 | 985088 .. +3000000 sectors | ~1.43 GiB | **data / writable (ReiserFS)** |

```python
p4_start, p4_sectors = 985088, 3000000   # writable area / remaining CF
```

hda4 is formatted as ReiserFS, not ext2, because the stock mount command uses
the ReiserFS-only `nolog` option — an ext2 hda4 makes the vendor mount fail
with `EINVAL` and `/writable` never appears (see ZD1200-LAB-GUIDE.md hint #6).

### The formatting step

`make-synthetic-cf.py` formats hda4 out-of-band and byte-copies the result
into the disk image (`make-synthetic-cf.py:80-96`):

1. creates a temp file and truncates it to `p4_sectors * 512` bytes,
2. runs `mkreiserfs -f -q <tempfile>` on it (requires `reiserfsprogs` on the
   build host, or `MKREISERFS` to override),
3. streams the fresh filesystem into the disk at `p4_start * 512`.

The output of a build confirms it:

```
hda4 data : sectors 985088..3985088 (ReiserFS)
```

### The volume is left EMPTY

The freshly formatted ReiserFS gets **no seed, no skeleton, no payload**.
The script's docstring states this explicitly:

> The data partition starts empty like a factory-fresh volume: `sys_init` and
> `rc.pre_ac_init` create /writable/etc, the airespider/config/dump
> directories, certs and SSH keys themselves on first boot.

So the state of hda4 when QEMU first boots it is: a valid, empty ReiserFS
volume (journal, root dir, nothing else).

---

## 2. Who fills it in (vendor first boot, not the lab)

The stock userspace initializes the empty volume on first boot:

- `etc/init.d/sys_init` finds the data partition by minor number
  (`_grep_datafs 4` → hda4) and mounts it with the stock options:
  ```
  mount -o rw,async,noatime,nolog /dev/hda4 /writable
  ```
  then `mkdir /writable/etc` if missing, creates `/writable/etc/system`, and
  mounts a tmpfs over `/writable/etc/airespider-images/firmwares/supportxt`
  (size 4m).
- `etc/rc.pre_ac_init` then creates the rest of the skeleton:
  `/writable/etc/airespider`, `/writable/etc/config`,
  `/writable/etc/airespider/dump`, the airespider-images firmware dirs, etc.
- Certificates (`setupRootCA()` → `/writable/etc/airespider/certs`, with the
  `ok` marker) and SSH host keys are generated by the vendor code on first
  boot.

Evidence from a lab boot (`log`):

```
REISERFS (device hda4): found reiserfs format "3.6" with standard journal
/dev/hda4 on /writable type reiserfs (rw,noatime,nolog)
tmpfs on /writable/etc/airespider-images/firmwares/supportxt type tmpfs (rw,relatime,size=4m)
```

## 3. Persistence and reset

- The lab boots `zd1200-vm.qcow2`, a qcow2 overlay whose backing file is
  `synthetic-cf.img`.  Every write to `/writable` during a run lands in the
  overlay, so config/certs/keygen survive across reboots.
- `./run-zd1200-lab.sh --reset-disk` deletes both `synthetic-cf.img` and
  `zd1200-vm.qcow2`; the next launch rebuilds hda4 from scratch → an empty
  factory volume again (the wizard re-runs).
